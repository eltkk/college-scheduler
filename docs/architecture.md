# Архитектура первой версии

## Хранение

Один колледж обслуживается одной записью `workspace` с типизированным состоянием в PostgreSQL JSONB. Состояние содержит настройки, справочники, подтверждённую нагрузку, исходные плановые строки и текущие занятия. Версия формата: `schema_version=1`. Pydantic запрещает неизвестные поля и проверяет каждую сущность; общий валидатор проверяет ссылки и межсущностные ограничения.

Пользователи, сессии, попытки входа, документы импорта, задачи генерации и журнал версий хранятся в отдельных SQL-таблицах. Структура SQL управляется Alembic. Изменение формата состояния требует отдельной миграции JSON; неподдерживаемый номер формата отклоняется.

Для четырёх составителей выбран простой общий транзакционный замок вместо множества бронирований и блокировок по ресурсам. Это позволяет проверить пересечения между специальностями и курсами за одну транзакцию. Цена решения: запись и проверка всего текущего состояния при каждой правке, полный снимок в истории. Это не схема для множества колледжей или десятков тысяч одновременно редактируемых записей. После получения полного годового объёма измеряются время проверки, размер состояния/истории и генерация; при необходимости ресурсы и занятия выделяются в SQL-таблицы без изменения пользовательского API.

## Сохранение и конфликты

1. Браузер отправляет исходный номер версии и правку.
2. Сервер блокирует `workspace` через `SELECT FOR UPDATE`.
3. При несовпадении версии возвращает 409 без записи.
4. Применяет правку к копии, проверяет ссылки, календарь, часы, занятость, вместимость и переходы.
5. Сохраняет новое состояние и снимок истории в одной транзакции, увеличивает версию.

PostgreSQL является обязательным для совместной эксплуатации. SQLite применяется только в локальной разработке и большинстве быстрых тестов, её блокировки не заменяют PostgreSQL-проверку.

Браузер обновляет данные каждые 15 секунд, пока нет открытой формы. Во время правки новая версия показывает предупреждение, введённые данные не заменяются автоматически. Восстановление создаёт новую версию; ограничение хранения применяется ко всем правкам.

## Расчёт

Запрос создаёт задачу со снимком состояния и исходной версией. `worker` берёт задачу, строит CP-SAT-модель с необязательными интервалами: NoOverlap для преподавателей и участников, Cumulative для вместимости и параллельного использования помещения. Подгруппы приводятся к конечным непересекающимся единицам студентов. Лимит родительской группы применяется к каждой подгруппе, а не к сумме параллельной практики.

Закреплённые и невыбранные занятия остаются обязательными. Вариант проверяется общим валидатором независимо от модели, отдельно сверяется точное число часов каждой выбранной потребности. Существующее расписание во время расчёта не меняется. Применение проходит обычную транзакцию и отклоняет устаревший снимок.

Статусы: optimal, feasible, infeasible, timeout, invalid. Неполный результат не применяется. У задач есть лимит решателя и общий аварийный лимит; зависшие после остановки процесса получают ошибку при следующем опросе worker. Разворачивается один worker. Очередь и результат переживают перезапуск в PostgreSQL.

## Доступ

Четыре учётные записи создаются вне интерфейса из секретной переменной, права одинаковы. Argon2, случайные непрозрачные сессии с хешем токена в БД, HttpOnly/SameSite cookies, CSRF-заголовок, лимит неверных входов и TrustedHost. В эксплуатации cookies Secure и HTTPS. Пароли не попадают в git. Сброс пароля через CLI завершает все сессии пользователя.

Полные снимки истории содержат пользовательские данные. Бэкапы нужно защищать так же, как рабочую базу; частоту и срок хранения согласовать с колледжем. История хранит последние 200 состояний (настраивается через HISTORY_VERSIONS), они доступны в интерфейсе. Более старые снимки удаляются в транзакции очередной правки; для долгого хранения служат отдельные резервные копии. Полный источник задачи генерации освобождается после завершения расчёта, результат и исходный номер версии сохраняются.
